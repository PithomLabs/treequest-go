Here’s a structured overview for porting **TreeQuest** to Go as a **general-purpose AB‑MCTS library**, keeping your EBP evaluation use‑case separate but conceptually aligned.

---

## 1. What TreeQuest Brings (AB‑MCTS Recap)

TreeQuest implements **Adversarial‑Constructive Monte Carlo Tree Search** (AB‑MCTS), where two roles alternate:

- **Constructive agent (A)** proposes improvements, additions, or solutions.
- **Adversarial agent (B)** critiques, finds flaws, or suggests counter‑arguments.
- **Evaluator (E)** scores a state (the outcome of an A‑or‑B move).

The tree grows depth‑first by alternating between A and B. At each node, the search selects, expands, simulates (or directly evaluates), and back‑propagates a reward.

Your Go library should capture this **algorithm only**, not any domain logic.

---

## 2. Core Abstractions for the Go Library

Define **interfaces** that keep the library completely separated from physics, LLMs, or any specific evaluator:

```go
// State holds all information needed to represent a tree node.
type State interface {
    // Clone returns a deep copy, used when expanding new branches.
    Clone() State
}

// Action represents a move that transforms a state.
type Action interface {
    // Apply mutates a state in-place (or returns a new one) after the action.
    Apply(State) State
}

// Agent generates possible actions from a given state.
// The library will call either the constructive or adversarial agent
// depending on the current tree depth.
type Agent interface {
    GenerateActions(ctx context.Context, state State) ([]Action, error)
}

// Evaluator scores a terminal (or intermediate) state.
type Evaluator interface {
    Evaluate(ctx context.Context, state State) (float64, error)
}
```

**Why this separation:**  
- The `State` can be *anything* (a string, a struct with paper claims, a JSON blob).  
- `Action` can be a simple wrapper around an LLM prompt result.  
- `Agent` and `Evaluator` are the **only places where LLMs appear** – and you implement them in the application layer.

## 3. AB‑MCTS Configuration and Budget Control

Define a configuration struct that includes all tuning knobs, plus a clear **budget mechanism**:

```go
type ABMCTSConfig struct {
    // How many iterations (full selection->backpropagation cycles) to run.
    MaxIterations int
    // UCB exploration constant.
    UCBConstant float64
    // Budget – total number of LLM calls allowed.
    // (Can be split into MaxConstructiveCalls, MaxAdversarialCalls.)
    MaxLLMCalls int
    // Timeout for the whole search.
    Timeout time.Duration
    // Optional: random seed.
    Seed int64
}
```

During execution, the library counts how many times it calls `Agent.GenerateActions` and `Evaluator.Evaluate`. When `MaxLLMCalls` is reached, the search stops and returns the best action so far.

**Budget flag in the output:**  
After the search, the library can return statistics (`SearchStats`) that include `ConstructiveCallsUsed`, `AdversarialCallsUsed`, `EvaluatorCallsUsed`. Your EBP application can attach this information to the final research paper (e.g., as a metadata field or a “turns used” flag). This is clean: the library provides the data, the application decides how to display it.

## 4. The AB‑MCTS Algorithm in Go

### 4.1 Node Structure
Each node in the search tree keeps track of visits, total value, its parent, and a slice of children.

```go
type Node struct {
    state       State
    action      Action       // action that led to this node
    parent      *Node
    children    []*Node
    visits      int
    totalValue  float64

    // Whether this node was generated by a constructive (true) or adversarial (false) agent.
    // You can also infer it from depth parity.
    isConstructive bool
}
```

### 4.2 Tree Search Loop
```go
func (s *Search) Run(ctx context.Context, rootState State) (*Node, SearchStats, error) {
    root := &Node{state: rootState, isConstructive: false} // root is not constructive; first move will be constructive
    for iter := 0; iter < s.config.MaxIterations; iter++ {
        select {
        case <-ctx.Done():
            return root, stats, ctx.Err()
        default:
        }
        if s.callCount >= s.config.MaxLLMCalls {
            break
        }
        leaf := s.selectNode(root)
        // Determine whose turn it is at the leaf.
        agent := s.agentForNode(leaf)
        children, err := agent.GenerateActions(ctx, leaf.state)
        if err != nil { /* handle gracefully, maybe skip iteration */ }
        s.expand(leaf, children, agentIsConstructive)
        // Instead of a full rollout, evaluate the leaf directly (common in LLM‑based MCTS).
        reward, err := s.evaluator.Evaluate(ctx, leaf.state)
        if err != nil { /* ... */ }
        s.backpropagate(leaf, reward)
    }
    return s.bestChild(root), stats, nil
}
```

### 4.3 Agent Assignment
```go
func (s *Search) agentForNode(node *Node) Agent {
    // Root expects first move from constructive agent.
    if node.parent == nil {
        return s.constructiveAgent
    }
    // Alternate: if parent was constructive, child is adversarial, and vice versa.
    if node.isConstructive {
        return s.adversarialAgent
    }
    return s.constructiveAgent
}
```

### 4.4 Selection (UCB1)
```go
func (s *Search) selectNode(node *Node) *Node {
    for len(node.children) > 0 {
        var best *Node
        bestScore := math.Inf(-1)
        for _, child := range node.children {
            exploitation := child.totalValue / float64(child.visits)
            exploration := math.Sqrt(2 * math.Log(float64(node.visits)) / float64(child.visits))
            ucb := exploitation + s.config.UCBConstant * exploration
            if ucb > bestScore {
                bestScore = ucb
                best = child
            }
        }
        node = best
    }
    return node
}
```

### 4.5 Concurrency
For performance, multiple simulations can run in parallel using goroutines. A common pattern is:

- Use a pool of workers.
- Each worker runs `selectNode + expand + evaluate + backpropagate`.
- Shared `Node` must be protected by a mutex (or use atomic operations for visit counts and total value).
- For simplicity, start with a **single‑goroutine** version, then add a `sync.Mutex` on the root and use atomic increments for leaf statistics.

## 5. Making the Library General‑Purpose

**The library must not know about EBP, Lean, or any specific LLM.** It only knows:

- The `State` interface.
- The `Agent` and `Evaluator` interfaces.
- The AB‑MCTS algorithm.

**How you achieve generality:**

1. **Domain logic lives outside** – your EBP codebase defines a concrete `PaperState` struct that implements `State`, and `ConstructiveAgent`, `AdversarialAgent`, and `Evaluator` that wrap LLM API calls.

2. **No hard‑coded LLM calls** – the library never calls an LLM; it calls `Agent.GenerateActions` and `Evaluator.Evaluate`. If you want to use a mock or a simple rule‑based agent, you just implement those interfaces accordingly.

3. **Budget control is a search parameter** – any application can set `MaxLLMCalls`. The library reports usage; the application can use that to set a “turns used” flag.

4. **Output format is up to the application** – the library returns `bestChild.state` (and statistics). The EBP application can marshal that into a paper with a flag, or a JSON report, or whatever it needs.

This design is **clearly good**: it follows the single‑responsibility principle. The tree search algorithm is one piece; the physics‑audit logic is another; and the LLM plumbing is a third. All are cleanly decoupled.

## 6. EBP Use‑Case as a Separate Codebase

Your EBP implementation would:

- Define a `State` that holds the paper’s claims, evidence, debt items, etc.
- Implement `ConstructiveAgent` (worker A) that asks an LLM to retire a debt item, clarify a claim, or add evidence.
- Implement `AdversarialAgent` (worker B) that asks an LLM to find missing bridges, overclaims, or hidden assumptions.
- Implement `Evaluator` that scores the state using the EBP criteria (debt retired, final‑truth language present, etc.).

**Search flow example:**

- Start state: a raw paper entry with full debt.
- At depth 0 (constructive), agent A proposes a refined claim or map.
- At depth 1 (adversarial), agent B points out a missing null model.
- At depth 2 (constructive), agent A adds a null model.
- …
- The evaluator scores each resulting state; the search converges to a state with minimal debt.
- After the search, the application takes the best state, formats it as a research paper, and attaches a metadata field like `"turns_used": 12` (from `SearchStats`).

**Budget flag:** This is entirely reasonable. The number of LLM calls is a cost metric; exposing it helps users understand resource consumption and can be used for later rate‑limiting or cost estimation. The design is sound because the library does not prescribe *how* to use that flag—it simply provides the data.

## 7. Implementation Notes for Go

- **Error handling:** LLM calls can fail; design `Agent` and `Evaluator` methods to return errors. The search loop can retry or skip that expansion.
- **Context deadlines:** Use `context.Context` to cancel long‑running searches or respect an HTTP server timeout.
- **Testing:** Write tests with mock agents that return deterministic actions; verify tree statistics.
- **Packaging:**  
  ```
  github.com/yourorg/treequest/       (library)
  github.com/yourorg/ebp-workbench/   (application, imports treequest)
  ```
- **Documentation:** The library API should be clear that it implements AB‑MCTS; the user only needs to provide concrete implementations of `State`, `Agent`, and `Evaluator`.

## 8. Conclusion

You can build a clean, general‑purpose TreeQuest port in Go by:

- Defining minimal, LLM‑agnostic interfaces.
- Implementing the core AB‑MCTS loop with selection, expansion (alternating agents), evaluation, and backpropagation.
- Adding budget tracking and exposing usage statistics.
- Letting your EBP use‑case live in a separate package that implements those interfaces and formats the output as a paper with a “turns used” flag.

This decoupling is not just good design—it’s exactly what the Elephant Bridge Protocol encourages: keep the *protocol* (here, the search algorithm) separate from the *tool* (the LLMs) and the *domain* (physics claims). The result is a library that can be reused for any adversarial‑constructive reasoning task, not just EBP audits.
