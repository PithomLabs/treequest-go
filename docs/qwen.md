# From TreeQuest to `treequest-go`: An Architectural Blueprint for a General-Purpose Go MCTS Toolkit

## Core Principles of Decoupling and Generality

The primary objective of developing `treequest-go` is to create a general-purpose, reusable toolkit for Monte Carlo Tree Search (MCTS) that is entirely decoupled from any specific application domain, including Large Language Models (LLMs), scientific paper evaluation, or the EBP 2.1 framework <Research Goal>. Achieving this level of generality requires a foundational architecture built upon the principle of strict separation of concerns, where the core mechanics of the search algorithm are cleanly segregated from the domain-specific logic required to apply it. This approach ensures that the library remains a pure tool for exploration and optimization, free from assumptions about its inputs, outputs, or underlying computational agents. The central mechanism for enforcing this decoupling in Go is the extensive use of interfaces, which define clear contracts between the library and its consumers [[2](https://stackoverflow.com/questions/51912841/golang-transactional-api-design), [94](https://dev.to/arasosman/understanding-gos-type-system-a-complete-guide-to-interfaces-structs-and-composition-2025-3an)]. Instead of embedding concrete implementations of evaluators, generators, or state representations, the library will expose interfaces that users must satisfy with their own domain-specific code. This pattern, known as consumer-defined interfaces, empowers developers to integrate simulators, heuristic functions, local models, or external service calls without any modification to the core library itself [[50](https://dev.to/dentedlogic/the-repository-pattern-done-right-consumer-defined-interfaces-in-go-1f14)].

This design philosophy is not only aligned with Go's language features but also reflects best practices in software architecture, such as those found in Domain-Driven Design (DDD), where complexity is managed by connecting the implementation to an evolving model of the domain [[32](https://stackoverflow.com/questions/54873864/golang-and-ddd-domain-modeling), [33](https://dev.to/stevensunflash/using-domain-driven-design-ddd-in-golang-3ee5)]. By treating components like `Evaluator`, `Generator`, and `State` as interfaces rather than concrete types, `treequest-go` can support a vast array of use cases, from game-playing bots and mathematical problem-solving to complex reasoning tasks [[6](https://dl.acm.org/doi/10.1145/3001773.3001797), [74](https://www.researchgate.net/publication/320003615_MCTSUCT_in_solving_real-life_problems)]. The success of SakanaAI's original TreeQuest library in Python, which provides a flexible API for customizing scoring and logic, serves as a precedent for this level of extensibility [[10](https://hyper.ai/cn/stories/662bbc53073607c784bc1f74dbbd5c79)]. The goal for `treequest-go` is to translate this flexibility into idiomatic Go, ensuring that the library's core is agnostic to the nature of the "agents" or "models" performing the evaluation and expansion steps of the AB-MCTS algorithm. This neutrality prevents developers from making unwarranted assumptions that the library is exclusively for machine learning applications, thereby broadening its potential utility [[21](https://www.seangoedecke.com/mcts-and-llms/)]. The library's responsibility is to manage the tree structure, control the flow of the search process, and aggregate results; all other domain-specific intelligence resides outside its purview.

A key aspect of this decoupling strategy is the deliberate avoidance of terminology that carries semantic weight tied to specific paradigms, most notably the term 'model' . Using 'model' implies a connection to machine learning and neural networks, which would unnecessarily constrain the library's perceived purpose. A more appropriate vocabulary includes terms like `Evaluator`, `Action`, `Generator`, or `PolicyFunction`, which are more generic and applicable across different fields. For example, an `Evaluator` could be a physics simulator calculating the stability of a structure, a rule-based system checking a proof, or a call to an external service for sentiment analysis [[36](https://arxiv.org/html/2510.09988v1)]. This terminological shift is crucial for building a truly general-purpose toolkit. Furthermore, the library should avoid embedding any logic related to academic review, paper assessment, or specific multi-agent protocols like EBP 2.1 within its core files <Research Goal><Conversation History>. These concepts represent a specific application layer that should exist as a separate consumer project. The core library must remain a clean slate, providing the fundamental tools for tree-based search so that downstream applications can build their own unique workflows on top of it. This separation ensures long-term maintainability and allows the library to evolve independently of any single use case. The architecture should be designed to be extended through composition rather than inheritance, leveraging Go's struct composition over traditional class-based inheritance to create explicit, flexible, and modular systems [[94](https://dev.to/arasosman/understanding-gos-type-system-a-complete-guide-to-interfaces-structs-and-composition-2025-3an)]. The ultimate measure of success for `treequest-go` will be its ability to serve diverse problems—from optimizing delivery routes in a multi-agent system [[53](https://www.nature.com/articles/s41598-025-10371-w)] to exploring reasoning paths in knowledge graphs [[39](https://aclanthology.org/2025.findings-acl.484/)]—without requiring changes to its internal implementation.

## API Design: The `Ask`/`Tell` Paradigm for Asynchronous Flexibility

The choice of the primary public API for `treequest-go` is a critical architectural decision with profound implications for usability, concurrency, and budget control. The user has identified two potential models: a `Step(generateFns)` function that encapsulates a complete MCTS iteration, or an `Ask`/`Tell` interface that separates the process of requesting work from providing results . After careful analysis of these options in the context of creating a general-purpose library, the `Ask`/`Tell` paradigm is unequivocally the superior choice. It offers greater flexibility, particularly for handling asynchronous evaluations and implementing fine-grained, application-level budgets, which are essential for non-trivial use cases involving LLMs or other external services.

The `Step()` approach, while simple and self-contained, presents significant limitations. A typical `Step` function would take one or more generation functions as input and execute the full sequence of Selection, Expansion, Simulation, and Backpropagation in a single, blocking call [[31](https://stackoverflow.com/questions/56093505/how-do-i-get-the-following-golang-mcts-example-running)]. This push-based model tightly couples the act of generating new states with the internal state management of the tree. While adequate for purely synchronous simulations where expansion is instantaneous, it becomes cumbersome when dealing with expensive or externally-hosted evaluators. Waiting for an LLM response, a database query, or a physical simulation to complete inside a tight loop within the `Step` function would lead to inefficient resource utilization and a poor user experience. More importantly, it makes granular budget enforcement difficult. There is no natural point within a single `Step()` call to check if a per-turn limit, token budget, or monetary cost has been exceeded before proceeding.

In contrast, the `Ask`/`Tell` interface provides a pull-based, asynchronous-friendly architecture that directly addresses these shortcomings. This paradigm exposes two primary methods on the main searcher object:
1.  `Ask()`: The calling application requests the next node that needs to be expanded. The library returns a `Node` object representing a new state.
2.  `Tell(node, evaluationResult)`: The calling application provides the result of evaluating the given node back to the library. The library then handles the backpropagation of the score up the tree.

This pull-based model is inherently more flexible and powerful. It decouples the search engine's state management from the potentially slow and external evaluation process [[115](https://dev.to/anubhavitis/push-vs-pull-api-architecture-1djo), [116](https://boomi.com/blog/push-versus-pull-integration-explained/)]. The caller can fetch a node via `Ask()`, perform the necessary work (e.g., make an LLM API call, run a heuristic), and then signal completion by calling `Tell()` at a later time, perhaps even asynchronously. This is ideal for scenarios where evaluation is I/O-bound or involves waiting for a third-party service. Furthermore, this model provides explicit hooks for budget management. After each `Tell()` operation, the consuming application can inspect its internal counters for turns, tokens, or cost and decide whether to continue the search loop. This aligns perfectly with the need to enforce application-level budgets, such as limiting the number of turns for worker agents in the EBP 2.1 use case [[25](https://arxiv.org/html/2602.09574v2)]. The `Ask`/`Tell` interface naturally supports batching as well; an application could call `Ask()` multiple times to get a list of candidate nodes, evaluate them concurrently, and then call `Tell()` once for each result. While the `Step` function could be implemented as a convenience wrapper *on top of* the `Ask`/`Tell` core for simpler, synchronous use cases, the latter should be the foundation of the public API to ensure maximum generality and power.

| Feature | `Step(generateFns)` Approach | `Ask`/`Tell` Approach |
| :--- | :--- | :--- |
| **Execution Model** | Push-based, synchronous, single-threaded per step [[31](https://stackoverflow.com/questions/56093505/how-do-i-get-the-following-golang-mcts-example-running)] | Pull-based, asynchronous, multi-threaded friendly [[115](https://dev.to/anubhavitis/push-vs-pull-api-architecture-1djo), [116](https://boomi.com/blog/push-versus-pull-integration-explained/)] |
| **Evaluation Handling** | Evaluation is performed synchronously within the library's control flow. Difficult to handle external, slow, or async evaluators. | Evaluation is handled completely by the consumer. Ideal for LLM calls, simulators, and other external services [[68](https://dev.to/isaachagoel/read-this-before-building-ai-agents-lessons-from-the-trenches-333i)]. |
| **Budget Control** | Granular budget enforcement (per-turn, per-token) is difficult as evaluation is internal to the step. | Explicit budget checks are possible after each `Tell()` call, allowing for fine-grained control by the consumer [[25](https://arxiv.org/html/2602.09574v2)]. |
| **Concurrency Support** | Limited; parallelization would require significant refactoring of the step function. | Naturally supports batching and concurrent evaluation of multiple nodes requested by the consumer. |
| **Usability** | Simpler for basic, synchronous use cases. | Slightly more boilerplate for the user, requiring an explicit interaction loop, but offers much greater flexibility. |

Ultimately, the `Ask`/`Tell` paradigm is more idiomatic for Go when dealing with external stateful processes and provides the necessary architectural hooks to build sophisticated, real-world applications. It respects the boundary between the pure search algorithm and the application logic, making it the clear recommendation for the `treequest-go` API.

## Terminology and Data Representation for Semantic Neutrality

To fulfill the research goal of creating a library fully decoupled from LLMs and EBP-specific logic, a deliberate and consistent effort must be made to establish a neutral vocabulary and data representation scheme . The language used in the API, documentation, and core logic profoundly influences how developers perceive and use a library. Adopting terms traditionally associated with reinforcement learning and large language models, such as `Model`, `Policy`, `Value`, `Reward`, and `Verifier`, would create a strong semantic association that could deter developers working in other domains and limit the library's perceived scope . Therefore, a conscious shift towards more generic, universally understood computer science and mathematics terminology is essential for achieving true generality.

The following table outlines a proposed vocabulary shift to promote semantic neutrality:

| Traditional ML/AI Term | Proposed Neutral Alternative | Justification |
| :--- | :--- | :--- |
| `Model` | `Evaluator` / `Scorer` | Broadens the concept beyond neural networks to include any function that can assign a value to a state, such as a heuristic, a physics simulator, or a database query. [[36](https://arxiv.org/html/2510.09988v1)] |
| `Policy` | `ActionGenerator` / `ExpansionStrategy` | Describes the process of generating successor states without implying a probabilistic distribution learned from data. |
| `Value` | `Score` / `Utility` | A more general term for the numeric outcome of an evaluation, applicable to game scores, fitness functions, or correctness metrics. |
| `Reward` | `RawScore` / `EvaluationOutput` | Represents the unprocessed output from an `Evaluator`. The distinction highlights that the core library may normalize this value. [[23](https://arxiv.org/html/2505.15858v3)] |
| `Verifier` | `Assessor` / `Judger` | Applicable to any entity that assesses the quality of a solution, whether it's an LLM judging a paper or a program checking a proof. [[47](https://zhuanlan.zhihu.com/p/935860735)] |
| `Prompt` | `State` / `Query` | `State` is the standard term in MCTS literature for the information defining a node in the search tree. [[74](https://www.researchgate.net/publication/320003615_MCTSUCT_in_solving_real-life_problems)] |
| `Response` | `Action` / `Result` | Describes the output of an `Evaluator` or the action taken to reach a new state. [[38](https://www.mdpi.com/2076-3417/13/3/1936)] |

This change in terminology is not merely cosmetic; it fundamentally reframes the library as a tool for systematic exploration and optimization, applicable to a wide range of problems. For instance, instead of "searching against a verifier," the library facilitates a process of systematically exploring a state space guided by an `Evaluator`.

Alongside terminology, the representation of scores is another critical area for ensuring generality. While many MCTS algorithms internally rely on normalized rewards (typically in the [0,1] interval) for calculations like the Upper Confidence Bound for Trees (UCT) formula [[23](https://arxiv.org/html/2505.15858v3)], the core library should not force this constraint on its users. A robust design would involve a separation of concerns: the user-provided `Evaluator` returns a raw score in whatever format is native to their domain (e.g., an integer, a floating-point number, a string, or a complex struct). The library's backpropagation logic would then be responsible for normalizing this raw score into its internal `[0,1]` representation. This normalization could be based on a global understanding of the problem's theoretical minima and maxima or on statistics gathered during the search itself.

To accommodate the rich context that often accompanies an evaluation, the library must provide a mechanism for attaching arbitrary metadata to each node. This metadata field should be a generic container, such as `map[string]interface{}` or a more structured serializable format like CBOR [[153](https://cbor-diag.readthedocs.io/)]. This allows users to store information that the core library does not interpret but is crucial for the application, such as the full text of an LLM-generated paragraph, intermediate reasoning steps, citations from a paper review, or performance metrics from a simulation. This feature is vital for debugging, interpretability, and enabling more sophisticated post-processing of the search results. By adopting a neutral vocabulary and a flexible data representation scheme that separates raw evaluation from internal state, `treequest-go` can be positioned as a versatile and powerful search toolkit, accessible and valuable to a much wider audience beyond the AI and LLM communities.

## Budget Management and State Persistence Boundaries

A crucial aspect of designing a reusable and robust MCTS library is clearly demarcating the responsibilities for budget enforcement and state persistence between the core library and its consumer applications. The user's requirement to separate generic tree-search limits from application-specific budgets like LLM turn counts is a key insight that should guide this architectural decision . Similarly, the desire to implement checkpointing for long-running searches necessitates a design that cleanly separates state management from I/O operations [[56](https://stackoverflow.com/questions/10498897/is-it-possible-to-interrupt-a-process-and-checkpoint-it-to-resume-it-later-on)]. A well-defined boundary ensures that the core library remains pure, focused, and portable, while providing the necessary hooks for applications to implement their own resource management and durability strategies.

The division of budget enforcement responsibilities should be based on the nature of the constraint. Generic, hard limits that are intrinsic to the MCTS algorithm's mechanics should be enforced within the library itself. These include:
*   **`MaxNodes`**: A hard cap on the total number of nodes the tree can contain. This prevents runaway memory consumption and is a common safeguard in MCTS implementations [[7](https://pypi.org/project/monte-carlo-tree-search/)].
*   **`MaxDepth`**: A limit on the depth of any branch in the search tree, preventing excessively long, narrow explorations.
*   **`MaxIterations`**: A cap on the total number of complete playouts or `Step` cycles the algorithm will execute.

These in-core budgets are essential for ensuring the library's stability and predictable resource usage. They form the fundamental constraints of the search process.

Conversely, soft, application-level budgets that are external to the core algorithmic logic must be managed entirely by the consuming application. These budgets are highly contextual and vary significantly between use cases. For the specified EBP 2.1 physics paper evaluation, these would include:
*   **`MaxTurns`**: A limit on the number of actions the constructive (A) and adversarial (B) agents can take. This corresponds directly to the user's request for a "turn budget" .
*   **`MaxTokens`**: A ceiling on the total number of tokens consumed in LLM API calls.
*   **`MaxCost`**: A monetary budget for LLM interactions.
*   **`MaxTime`**: A wall-clock time limit for the entire search process.

The `Ask`/`Tell` API design is particularly well-suited for managing these external budgets. The consumer application can wrap the interaction loop, incrementing counters for turns or tokens after each `Tell()` call and breaking the loop if any budget is exceeded. The library itself should expose a method like `IsBudgetExceeded()` or simply track this state, allowing the consumer to query it before requesting further work. This clear separation of concerns is vital; the library's job is to find the best path, not to police the user's spending or time allocation.

Similarly, checkpointing and resuming a search should be an application-level concern. The core library should not be burdened with I/O operations, file formats, or persistence mechanisms. Instead, it should provide a clean API for exporting its entire internal state as a byte stream. This can be achieved through a `Marshal()` or `Snapshot()` function that serializes the root node and the entire tree structure into a format the user can choose. The choice of serialization format is entirely up to the application, depending on its needs:
*   **`encoding/gob`**: Go's native binary encoding is efficient for communication between Go programs but lacks cross-language support [[58](https://stackoverflow.com/questions/37618399/efficient-go-serialization-of-struct-to-disk), [83](https://stackoverflow.com/questions/41179453/difference-between-encoding-gob-and-encoding-json)].
*   **JSON**: Widely supported, human-readable, and excellent for interoperability with non-Go applications, though it may be less efficient in size and speed [[59](https://dev.to/manavkush/learning-microservices-with-gopart-3-serialization-5di1)].
*   **Protocol Buffers or MessagePack**: High-performance binary formats offering good cross-language support and smaller data sizes compared to JSON [[59](https://dev.to/manavkush/learning-microservices-with-gopart-3-serialization-5di1), [112](https://www.cnblogs.com/Dr-wei/p/11742261.html)].
*   **CBOR**: A compact binary format with a diagnostic notation similar to JSON, suitable for both efficiency and readability [[153](https://cbor-diag.readthedocs.io/)].

The consuming application is then responsible for taking this serialized byte stream and saving it to durable storage (a file, a database, etc.). Resuming the search would involve the reverse process: loading the byte stream and passing it to an unmarshaling function in the library to reconstruct the search state [[109](https://stackoverflow.com/questions/33689598/how-to-pause-resume-training-in-tensorflow), [110](https://dev.to/mukundakatta/durable-agent-state-checkpoints-resume-where-you-left-off-when-the-run-crashes-4f7i)]. This approach keeps the core library lightweight and portable, while giving users complete freedom in how they implement fault tolerance and long-running computation resilience.

## Idiomatic Go Implementation and Package Structure

When porting a library from another language, a critical decision is whether to replicate the original API surface or to embrace the idioms and patterns of the target language . For `treequest-go`, the overwhelming recommendation is to prioritize idiomatic Go design over maintaining direct compatibility with the Python `TreeQuest` library. While a thin compatibility layer might be considered in the future, the core of the library should be built from the ground up using Go's strengths: its simplicity, strong type system, excellent standard library for concurrency and networking, and established programming patterns [[3](https://www.linkedin.com/pulse/mastering-go-programming-idiomatic-approach-hemant-jain-kjorc), [131](https://blog.cloudflare.com/whats-inside-net-http-socket-late-binding-in-the-go-standard-library/)]. This approach will result in a more robust, maintainable, and intuitive library for Go developers.

One of the most important idiomatic patterns in Go for configuring complex objects is the **Options Pattern**, also known as Functional Options [[24](https://dev.to/sfundomhlungu/golang-master-class-functional-options-5a00), [79](https://learnku.com/articles/64514)]. Instead of creating numerous constructors or bloated structs with many optional fields, the library's main searcher object should be configured by passing a series of functions to its constructor. Each function modifies a configuration struct. This pattern is clean, scalable, and easy to use, as demonstrated by many libraries in the Go ecosystem. For example, setting budgets and search parameters would look like:
```go
searcher := NewSearcher(
    WithMaxNodes(10000),
    WithMaxDepth(50),
    WithEvaluator(myEvaluator),
    WithExpansionStrategy(myStrategy),
)
```
This approach is far more readable and extensible than traditional builder patterns or multiple constructor variants [[78](https://www.cnblogs.com/taadis/p/go-functional-options-pattern.html), [80](https://polarisxu.studygolang.com/posts/go/action/functional-options-pattern/)].

Regarding the overall package structure, a modular and versioned approach is advisable for long-term maintainability. A logical structure for the initial version would be:

```
treequest-go/
├── v0/
│   ├── abmcts.go     # Main AB-MCTS controller implementing the Ask/Tell API
│   ├── node.go       # Definition of the Node struct and its public methods
│   └── options.go    # Implementation of the Options Pattern for configuration
└── interfaces.go     # Top-level interfaces for Evaluator, StateProvider, etc.
```

This structure separates the core implementation (`v0/`) from the public-facing contract defined by the interfaces (`interfaces.go`). The `v0` subdirectory follows Go's module versioning convention, signaling that the API within is still under development and may have breaking changes. The `interfaces.go` file acts as the public API surface, defining the minimal set of behaviors the library expects from its dependencies.

For a v0.1 release, the following features should be prioritized to deliver a functional and stable core:
*   **Core Algorithm:** A complete and correct implementation of the AB-MCTS algorithm, including Selection, Expansion, Simulation, and Backpropagation.
*   **`Ask`/`Tell` API:** The primary public interface as the main entry point for interaction.
*   **Configuration:** A robust implementation of the Options Pattern to configure all key parameters and dependencies.
*   **State Management:** A well-defined `Node` struct containing pointers to parent and children, visit count, and the aggregated score/reward.
*   **Basic Exploration:** A standard UCT-style exploration strategy as the default selection policy.

Features that should be deferred to v0.2 or later include:
*   **Advanced Exploration Heuristics:** Variants of the UCT formula, Dirichlet noise for added exploration, etc., can be provided as optional strategies passed via the options.
*   **Parallelization:** While massively parallel MCTS exists [[61](https://openreview.net/forum?id=6k7VdojAIK), [62](https://arxiv.org/html/2605.08982v2)], a single-threaded implementation is sufficient for v0.1. Parallel execution logic can be layered on top later without changing the core API.
*   **Checkpointing:** As previously discussed, this should be an application-level feature, not part of the core library.

Finally, all logic specific to the EBP 2.1 physics paper evaluation—including the distinct roles of agents A, B, and E, the turn-based protocol, and the specific evaluation criteria—must reside entirely in a separate consumer application. This application will import `treequest-go` and use it as a black box to explore its problem space. It will implement the `Evaluator` interface to score candidate paper reviews and manage its own budgets for LLM calls. This strict separation is paramount to fulfilling the user's goal of a general-purpose library. The resulting `treequest-go` will be a clean, focused, and powerful tool for tree search, ready to be applied to a multitude of challenging problems far beyond its initial conception.
