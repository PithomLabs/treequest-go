# Implementation Plan - EBP-EVAL-SIMPLE-0004: Real-Provider Reviewer Schema Contract Hardening

## 1. Verdict and Scope

This plan addresses the ticket **EBP-EVAL-SIMPLE-0004: Real-Provider Reviewer Schema Contract Hardening**. 
All changes are contained strictly within the `ebp-paper-evaluator` codebase. There will be absolutely no modifications to the `treequest-go` repository.

## 2. Root-Cause Summary

An investigation of raw outputs from real-provider runs (such as those in `/home/chaschel/Desktop/physics/sakana/out/20260620_0318` and `my-paper-triple-review`) revealed that every successful API response failed strict JSON parsing. The root causes are:

1. **The `null` Schema shape defect:** In [triple_review.go](file:///home/chaschel/Documents/go/treequest/ebp-paper-evaluator/pkg/simple/triple_review.go#L118), the schema example is generated by marshaling an empty struct `ReviewerOutput{}`. Because Go slices are uninitialized, this serialized arrays as `null` (e.g., `"main_claims": null`).
2. **Missing Inner Structure:** The models had no example showing the internal fields of a `ReviewerClaim` (such as `claim_id` or `claim_text`) or indicating that lists like `maps_identified` should be simple flat string arrays (`[]string`).
3. **Structured Deviations:** Lacking structure in the prompt's schema, models inferred details from the EBP 2.1 policy, returning arrays of complex objects for string arrays and nested objects for claims.
4. **Strict parser rejection:** Because `DisallowUnknownFields` is enabled in [DecodeFirstJSONObject](file:///home/chaschel/Documents/go/treequest/ebp-paper-evaluator/pkg/jsonutil/extract.go#L67), Go's JSON parser correctly threw errors for these incompatible shapes.

## 4. Schema Example Design

We will add a helper function in [triple_review.go](file:///home/chaschel/Documents/go/treequest/ebp-paper-evaluator/pkg/simple/triple_review.go) to construct a populated example:

```go
func reviewerOutputExample(c Config, reviewerID, modelID string) ReviewerOutput {
	debtIDs := []string{}
	for _, d := range c.Policy.IR.DebtItems {
		debtIDs = append(debtIDs, d.ID)
	}
	if len(debtIDs) == 0 {
		debtIDs = []string{"needMap", "needInvariant"}
	}

	mainClaims := []ReviewerClaim{
		{
			ClaimID:   "claim_1",
			ClaimText: "Precise candidate claim extracted from the paper.",
			EvidenceQuotes: []EvidenceQuote{
				{
					Quote:       "Exact quote copied from the paper.",
					SectionHint: "Abstract or Section 1",
				},
			},
			EBPDebts: debtIDs,
			Status:   "candidate_unreviewed",
		},
	}

	return ReviewerOutput{
		ReviewerID:             reviewerID,
		ModelID:                modelID,
		PaperSummary:           "Brief 2-3 sentence summary of the paper.",
		MainClaims:             mainClaims,
		MapsIdentified:         []string{"Map from proposed mathematical structure to observable physical quantity."},
		InvariantsIdentified:   []string{"Claimed invariant, conservation law, symmetry, or preserved quantity."},
		ToyChecksIdentified:    []string{"Suggested finite toy check or calculation."},
		NullModelsIdentified:   []string{"Alternative baseline explanation or simpler rival model."},
		ObstructionsIdentified: []string{"Technical blocker, missing derivation, or circularity risk."},
		FaithfulnessLimits:     []string{"Human faithfulness review was not performed."},
		OverclaimWarnings:      []string{"Do not treat this as proof or EBP promotion."},
		RecommendedNextSteps:   []string{"Extract exact equations and map them to EBP debts."},
		OverallAssessment:      "Candidate EBP assessment only.",
		Limitations: []string{
			"Automated candidate assessment only.",
			"Human faithfulness review was not performed.",
			"No EBP promotion is claimed.",
		},
	}
}
```

In `systemPrompt`, the marshaling will use this function:
```go
example := reviewerOutputExample(c, reviewerID, modelID)
schema, _ := json.MarshalIndent(example, "", "  ")
```

## 5. System Prompt Contract Changes

We will append the following explicit contract instructions to the generated system prompt in `systemPrompt`:

```text
Return exactly one JSON object.
Do not use Markdown fences.
Do not return prose before or after JSON.
Do not add unknown fields.
Do not rename keys.
All array fields must be arrays, never null. Use [] when there are no items.

Explicit Type Contracts:
1. The following fields MUST be arrays of strings ([]string):
   - maps_identified
   - invariants_identified
   - toy_checks_identified
   - null_models_identified
   - obstructions_identified
   - faithfulness_limits
   - overclaim_warnings
   - recommended_next_steps
   - limitations
   Do NOT return arrays of objects for those fields. Flatten rich details into concise strings.

2. 'main_claims' must be an array of objects with exactly these keys:
   - claim_id (string)
   - claim_text (string)
   - evidence_quotes (array of objects)
   - ebp_debts (array of strings)
   - status (string, must be "candidate_unreviewed")

3. 'evidence_quotes' must contain objects with exactly these keys:
   - quote (string)
   - section_hint (string)

4. 'ebp_debts' must be a flat array of strings containing only debt IDs from the active policy. Do not return a debt object or map.
```

## 6. Strict Parsing Preservation

* We will **preserve** the use of `jsonutil.ExtractFirstJSONObject` and `dec.DisallowUnknownFields()`.
* We will **explicitly reject** decoding into `map[string]any` or dynamic structures that hide malformed schema issues.
* The evaluator must continue to fail reviews that violate the schema structure.

## 7. Parseability-Aware Run-Status Design

We will add the following fields to `ScoringSummary` in [types.go](file:///home/chaschel/Documents/go/treequest/ebp-paper-evaluator/pkg/simple/types.go):

```go
type ScoringSummary struct {
	// ... (Preserve existing fields)
	CallRunStatus          string `json:"call_run_status"`
	ParseRunStatus         string `json:"parse_run_status"`
	AssessmentStatus       string `json:"assessment_status"`
	ReturnedResponseCount  int    `json:"returned_response_count"`
	ParseableReviewCount   int    `json:"parseable_review_count"`
}
```

The logic inside `Run` and `summarize` will populate these:
* **`call_run_status`:** `triple_review_complete` (3 calls returned), `partial_triple_review_two_reviewers` (2 returned), `partial_review_insufficient_for_agreement` (1 returned), `run_failed_no_reviewer_content` (0 returned).
* **`parse_run_status`:** 
  * `all_reviews_parseable` (if `parseable_review_count == returned_response_count` and `returned_response_count == 3`)
  * `partial_reviews_parseable` (if `parseable_review_count == 2`)
  * `one_review_parseable` (if `parseable_review_count == 1`)
  * `no_parseable_reviews` (if `parseable_review_count == 0` but `returned_response_count > 0`)
* **`assessment_status`:**
  * `candidate_assessment_available` (if `parseable_review_count == 3`)
  * `degraded_candidate_assessment_available` (if `1 <= parseable_review_count < 3`)
  * `assessment_unavailable_schema_parse_failed` (if `returned_response_count > 0 && parseable_review_count == 0`)
  * `run_failed_no_reviewer_content` (if `returned_response_count == 0`)

## 10. Optional Repair Mode Decision

We will design a `--repair-malformed-json` flag but keep it **disabled by default**. 

If enabled, it will invoke a lightweight repair process that cleans up obvious formatting issues (like trimming markdown code block fences if the LLM output wrapper fails) or calls a secondary structured extraction. We will define a `provenance.json` log schema:
```json
{
  "repair_attempted": true,
  "repair_succeeded": false,
  "original_parse_status": "review_parse_failed",
  "final_parse_status": "review_parse_failed"
}
```

## 13. Risks and Mitigations

* **Risk:** Model provider rejects the `response_format` JSON parameter (causes API error).
  * **Mitigation:** Gracefully handle the error. If a model fails to return anything due to API errors, mark that model's call status as `reviewer_call_failed` (meaning the run status is degraded but continues without crashing).
* **Risk:** The model ignores the prompt instruction and still generates markdown fences.
  * **Mitigation:** The robust `ExtractFirstJSONObject` logic already extracts the inner object even if it is enclosed inside a markdown fence.

## 14. Explicit Non-Goals

* We will **not** modify `treequest-go`.
* We will **not** weaken the JSON validator's strict structure and field checks.
* We will **not** allow self-assigned scores or claims of scientific truth in the generated EBP report.

---

## 15. Acceptance Criteria

* `systemPrompt` outputs a concrete, non-nil, fully-populated example JSON structure.
* Prompt explicitly forbids markdown fences, unknown keys, renamed keys, and object-arrays for string-list fields.
* Strict JSON decoding remains authoritative.
* Observed malformed response fixtures fail clearly in testing.
* Status flags (`call_run_status`, `parse_run_status`, `assessment_status`) reflect parseability failures accurately.
* Artifact bundles reflect degraded or unparseable runs without displaying misleading zero-scores.
* Reviewer temperature is forced to `0.0` or `0.1` for schema-following reliability.
* `go test ./...`, `go test -race ./...`, and `go vet ./...` all pass.
